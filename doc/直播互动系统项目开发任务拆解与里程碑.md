# 直播互动系统项目开发任务拆解与里程碑

**文档版本：V1.0**  
**项目名称：Live Interactive Platform**  
**核心技术栈：Go + Centrifugo + Redis + Kafka + MySQL**  
**配套文档：**
- 《基于 Centrifugo 的高并发直播互动系统技术方案书》
- 《直播互动系统详细设计说明书》
- 《直播互动系统压测与容量规划方案》

---

# 1. 项目目标

本项目目标是实现一套具备真实工程价值的高并发直播互动系统，重点解决：

- 大规模 WebSocket 长连接；
- 高并发弹幕广播；
- 高频点赞削峰聚合；
- 礼物订单与钱包一致性；
- Transactional Outbox；
- Kafka 异步事件体系；
- 热门直播间治理；
- 服务故障恢复；
- 性能压测与容量规划；
- 可观测性与生产部署。

项目最终不以“功能全部完成”为唯一验收标准，而以：

```text
功能正确
+
架构合理
+
数据一致
+
可以压测
+
可以定位瓶颈
+
可以故障恢复
+
有真实性能数据
```

作为最终交付目标。

# 2. 开发原则

## 2.1 不提前微服务化

一期部署：

```text
live-api
live-worker
centrifugo
redis
mysql
kafka
```

业务代码内部模块化。

只有当出现明确扩展需求后，才拆分：

```text
Gift Service
Danmaku Service
Room Service
Wallet Service
```

---

## 2.2 先正确，再高并发

开发顺序：

```text
业务正确性
    ↓
实时通信
    ↓
数据一致性
    ↓
异步化
    ↓
可观测性
    ↓
压力测试
    ↓
性能优化
    ↓
集群与容灾
```

禁止第一阶段直接尝试：

```text
百万 WebSocket
Redis Cluster
Kafka 大集群
Kubernetes
多区域部署
```

# 15. Issue 模板

每个 Issue 必须说明：

## Background

为什么需要这个功能。

## Goal

本 Issue 要解决什么问题。

## Design

实现方案。

## Tasks

```text
- [ ] ...
- [ ] ...
```

## Test

怎样验证。

## Done Definition

满足什么条件才允许关闭 Issue。

# 16. 示例 Issue

## [M4] 实现礼物订单幂等

### Background

客户端因为网络超时可能重复提交礼物请求。

### Goal

相同 Idempotency-Key 不允许重复扣款。

### Tasks

```text
- [ ] gift_orders 添加 request_id
- [ ] 添加 UNIQUE INDEX
- [ ] API 接收 Idempotency-Key
- [ ] 重复请求返回原订单
- [ ] 添加并发测试
```

### Test

并发发送：

```text
100 requests
```

使用相同：

```text
Idempotency-Key
```

### Done Definition

数据库：

```text
gift_orders = 1
wallet_transactions = 1
```

钱包仅扣款一次。
