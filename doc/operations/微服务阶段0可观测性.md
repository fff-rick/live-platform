# 微服务阶段 0：可观测性护栏

本阶段只建立迁移前基线和告警，不以告警阈值替代容量结论。所有阈值必须在多节点压测与故障演练后重新校准。

## 指标

| 指标 | 含义 | 迁移用途 |
| --- | --- | --- |
| `live_outbox_pending` | 未发布 Outbox 数 | 判断事件投递积压。 |
| `live_outbox_oldest_pending_age_seconds` | 最老未发布事件年龄；无积压时为 0 | 判断 Publisher 是否卡住，即使积压尚小也可发现。 |
| `live_kafka_consumer_lag` | 当前 consumer group/Topic/分区的近似 lag | Worker 独立扩容与故障排查依据。 |
| `live_kafka_consume_total` | Kafka 消费处理结果 | 观察重试、丢弃和提交失败。 |
| `live_db_pool_*` | 各进程的 MySQL 连接池使用和等待 | 为后续 API/Worker 副本数设连接总预算。 |
| `live_realtime_publish_total` | Centrifugo 发布成功/失败 | 观察实时平台故障。 |
| `live_danmaku_estimated_fanout_per_second` | 热点保护估计扇出 | 校验热点房间保护阈值。 |

指标使用低基数标签；禁止加入 `user_id`、`room_id`、订单号或事件 ID。命名保持 Prometheus 的 base-unit / `_seconds` 约定，参考 [Prometheus metric naming](https://prometheus.io/docs/practices/naming/)。

## 本地告警规则

`deployments/prometheus/stage0-alerts.yml` 已定义以下 warning：

- 5 分钟内持续存在超过 60 秒的未投递 Outbox；
- 10 分钟内任一 Kafka 分区 lag 持续超过 1,000；
- 10 分钟内数据库连接池平均每秒等待时间超过 100 ms。

Docker Compose 会将该规则挂载至 Prometheus。当前开发环境没有 Alertmanager，因此规则用于 Prometheus `/alerts` 页面和验证；生产环境必须接入 Alertmanager、通知路由和对应值班策略后才可作为事故通知。

## 扩缩容前检查

1. 记录每个 API/Worker Pod 的 `live_db_pool_max_open_connections`，计算所有副本之和，并为迁移、监控和管理连接预留数据库连接预算。
2. 对 Kafka 消费组同时观察 lag、处理失败与分区数；副本数超过可分配分区数不会提高同一消费组吞吐。
3. 对 Centrifugo 同时观察连接数、发布失败与端到端消息延迟。当前仓库未完成多节点连接容量证明，不得按单节点压测外推。
4. 在每次服务切流前记录 Outbox 年龄、lag、数据库池等待和实时发布失败的基线，并在切流后比对。
