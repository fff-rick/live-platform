# 直播互动系统详细设计说明书

**文档版本：V1.0**  
**对应架构方案：基于 Centrifugo 的高并发直播互动系统**  
**技术栈：Go + Centrifugo + Redis + Kafka + MySQL**

---

# 1. 文档目的

本文档用于指导直播互动系统的具体开发实现，重点定义：

- 服务模块；
- API；
- Centrifugo Channel；
- 实时消息协议；
- Redis Key；
- Kafka Topic；
- MySQL 数据模型；
- 幂等方案；
- 限流方案；
- 异常处理；
- 核心业务时序。

整体遵循：

```text
实时消息走 Centrifugo
高频状态走 Redis
异步事件走 Kafka
核心业务状态走 MySQL
```

# 2. 服务部署模型

一期采用：


# 4. Channel 设计

采用三个核心 Channel。

## 4.1 房间实时消息

```text
room:{room_id}:stream
```

用于：

- 弹幕；
- 礼物；
- 系统公告；
- 主播消息；
- 管理员消息。

例如：

```text
room:10001:stream
```

---

## 4.2 房间状态

```text
room:{room_id}:stats
```

用于：

- 当前在线人数；
- 累计点赞；
- 热度；
- 榜单变化。

状态类消息不要求完整消费历史，只关注最新值。

---

## 4.3 用户私有消息

```text
user:{user_id}
```

用于：

- 礼物发送结果；
- 余额更新；
- 禁言通知；
- 踢出直播间；
- 风控通知。

用户只能订阅自己的 Channel。

# 5. 实时事件协议

所有房间事件统一采用 envelope：

```json
{
  "event_id": "01JXXXX",
  "type": "danmaku",
  "room_id": 10001,
  "timestamp": 1786300000123,
  "data": {}
}
```

字段：

| 字段 | 说明 |
|---|---|
| event_id | 全局事件 ID |
| type | 事件类型 |
| room_id | 房间 ID |
| timestamp | 毫秒时间戳 |
| data | 业务数据 |

# 18. 钱包扣款设计

不采用：

```text
SELECT balance
```

然后在 Go 中修改。

推荐原子条件 UPDATE：

```sql
UPDATE wallets
SET balance = balance - ?
WHERE user_id = ?
  AND balance >= ?;
```

检查：

```text
RowsAffected == 1
```

否则余额不足。

所有金额使用：

```text
BIGINT
```

保存最小货币单位或平台虚拟币整数值，避免浮点数。

# 23. Outbox 发布流程

Worker 周期扫描：

```sql
SELECT ...
FROM outbox_events
WHERE status = 0
  AND next_retry_at <= NOW()
LIMIT 100;
```

发送：

```text
Outbox
 ↓
Kafka Produce
 ↓
Success
 ↓
status = PUBLISHED
```

失败采用指数退避：

```text
1s
5s
30s
1min
5min
```

长期失败进入告警。

# 26. Kafka 消费幂等

所有重要 Consumer 必须认为：

```text
消息可能重复
```

不得假设 Exactly Once。

消费端使用：

```text
event_id
```

建立：

```text
processed_event
```

或业务唯一键防止重复操作。

对于仅写分析日志的低价值任务，可以放宽幂等要求。

# 32. 弹幕降级策略

系统根据直播间状态分级。

### NORMAL

```text
全部弹幕广播
```

### HOT

```text
普通弹幕部分采样
礼物全部保留
主播消息全部保留
管理员消息全部保留
```

### PROTECT

```text
只广播高优先级事件
普通弹幕大比例采样
点赞降低刷新频率
```

例如：

```text
Normal Like Interval = 200ms
Protect Like Interval = 1000ms
```

# 33. 消息优先级

```text
P0 系统 / 封禁 / 核心控制事件
P1 礼物
P2 主播 / 管理员弹幕
P3 普通弹幕
P4 点赞动画
```

压力过大时按：

```text
P4 → P3
```

顺序降级。

禁止首先丢弃资产相关事件。

# 34. Centrifugo 配置原则

生产环境：

```text
Engine = Redis
```

节点：

```text
CF1
CF2
CF3
...
```

全部连接至 Redis。

建议不同 Namespace 使用不同 History 策略。

例如：

### stream

```text
history_size = 100~500
history_ttl = 30~60s
recovery = enabled
```

### stats

不需要大量 History。

因为状态消息只关心最新值。

# 35. 客户端重连

```text

 ↓
指数退避
 ↓
重新连接
 ↓
恢复 subscription
 ↓
History Recovery
```

退避示例：

```text

2s
4s
8s
最大 30s
```

同时加入随机 jitter，避免服务重启后百万客户端同时重连形成：


# 42. 设计底线

系统开发过程中禁止以下实现：

```text
客户端直接决定礼物金额
客户端直接广播礼物
每次点赞全房间广播
弹幕同步等待 MySQL
把 Centrifugo History 当数据库
依赖 MQ Exactly Once
用 connection 数直接代表真实用户数
无幂等地处理资金业务
```

这几项应作为 Code Review 和架构评审的强制检查项。
