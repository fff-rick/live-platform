# 微服务化与分布式演进计划

**状态：阶段 3 进行中**  
**适用范围：直播互动平面**  
**最后更新：2026-08-24**

## 1. 结论

本项目应演进为可按负载独立扩缩容的分布式互动平台，但**不应立即按 `internal/` 目录拆成大量微服务，也不应一开始实行一服务一数据库**。

当前实现已经是边界较清晰的模块化单体：`live-api` 与 `live-worker` 分进程运行，Worker 已通过 `WORKER_ROLES` 支持按角色启动。压测表明，优先需要独立扩缩容的是：

- 热点房间的实时扇出；
- Kafka 异步消费；
- 礼物与钱包的强一致事务；
- 不同类型 Worker 的资源配额。

因此采用“**先部署拆分，再业务拆分；先数据所有权，再物理独库**”的渐进式迁移，而非一次性重写。

## 2. 现状与驱动因素

现有核心组成如下：

```text
浏览器
  ├─ HTTP API ── live-api ── MySQL / Redis
  └─ WebSocket ─ Centrifugo ─ Redis

live-worker
  ├─ Outbox Publisher ───── Kafka
  ├─ Gift Consumer ──────── 实时礼物投递
  ├─ Danmaku Consumer ───── 弹幕归档
  └─ Stats / Like Worker ── 聚合与快照
```

已有压测结论应直接影响拆分优先级：

- 热点 Channel fan-out 是首个明确的实时链路压力点；当前策略将目标扇出控制在约 25K/s，热点与保护阈值分别约为 30K/s、40K/s。
- 单钱包是有意保留的事务串行边界；同钱包在约 90 强一致事务/s 附近饱和，不能以牺牲余额正确性解决。
- 多钱包负载下，当前环境的低延迟礼物基准约为 200 TPS、P99 约 67 ms；约 700--720 TPS 是高尾延迟的饱和观测值，不可作为生产 SLO。
- 当前 Kubernetes 基础设施中的 MySQL、Redis、Kafka 均为单副本，Kafka 为单 Broker、复制因子 1；它不是高可用分布式基础设施。

详见 [M7 容量决策](../benchmark/capacity.md) 与 [压测报告](../benchmark/README.md)。

## 3. 目标架构

```text
客户端
  │ HTTP
API Gateway / BFF
  ├─ 账户-房间服务 ───────── 用户、房间、治理
  ├─ 互动接入服务 ────────── 弹幕、点赞、观众、限流
  └─ 钱包-礼物服务 ────────── 钱包、订单、流水、Outbox
                                  │
                              Kafka 领域事件
       ┌───────────────────┬──────┼────────────────────┐
       │                   │      │                    │
弹幕归档服务          礼物投递服务  统计聚合服务       通知/风控服务（按需）
       │                   │      │
  Danmaku DB          Centrifugo API Redis / Centrifugo
                                                 │
                                          WebSocket 客户端
```

### 3.1 服务责任与数据所有权

| 服务 | 首次迁移内容 | 唯一写入所有者 |
| --- | --- | --- |
| 账户-房间服务 | 注册登录、个人资料、房间生命周期、禁言和封禁 | `users`、`live_rooms`、`room_mutes`、`room_bans` |
| 钱包-礼物服务 | 余额、充值、扣款、礼物订单、幂等、Outbox、礼物目录 | `wallets`、`wallet_transactions`、`gift_orders`、`outbox_events`、`gifts` |
| 互动接入服务 | 进退房、心跳、弹幕、点赞、限流、热点降级 | Redis 互动 key；不拥有钱包或房间表 |
| 弹幕归档服务 | 消费弹幕事件并保存可查询历史 | `danmaku_records` |
| 礼物投递服务 | 消费已完成送礼事件并发布实时消息 | 消费位点、幂等状态 |
| 统计聚合服务 | 在线数、点赞聚合、榜单读模型与快照 | Redis 统计 key、`room_like_snapshots` |
| 实时平台 | Centrifugo 集群、Channel 规则、连接观测 | 实时 Redis namespace / 集群 |

服务只能写入自身拥有的数据。读取其他服务数据时，优先消费事件形成读模型；无法避免的同步查询只能通过版本化 API 或 RPC 契约，不允许跨服务直连数据库。

### 3.2 实时平台

保留 Centrifugo 作为独立实时接入层，不自行实现 WebSocket 广播系统。项目现有 Redis engine 是多节点 Centrifugo 的必要基础：多节点可通过 Redis broker 投递跨节点 Channel 消息；随着连接数增加可横向扩容。官方说明见 [Centrifugo Engines and scalability](https://centrifugal.dev/docs/server/engines)。

实时 Redis 与业务 Redis 必须至少以独立 DB、账号、key 前缀隔离；进入大规模热点场景后再根据 Redis CPU、连接数、发布延迟决定是否分离为独立 Redis 集群或分片。不要在没有指标的情况下预先引入 Redis Cluster。

## 4. 一致性与事件设计

### 4.1 本地事务优先

礼物请求在**钱包-礼物服务内部**以一个 MySQL 本地事务完成：余额扣减、订单创建、流水记录和 Outbox 事件写入必须原子提交。跨服务不使用两阶段提交或分布式事务。

之后由 Outbox Publisher 将事件投递至 Kafka。消费者采用“至少一次投递 + 幂等处理”模型；现有 `processed_events` 可继续承担消费者去重职责。

当前只有礼物采用事务 Outbox。弹幕若要求“成功响应后最终必可归档”，也应迁移至互动服务的 Outbox；若允许仅实时可见、归档可降级，则保留直写 Kafka，但必须将 Kafka 故障从 API 进程启动和核心可用性中隔离。

### 4.2 领域事件契约

所有 Topic 消息采用版本化 envelope：

```json
{
  "event_id": "01J...",
  "event_type": "gift.order.completed.v1",
  "occurred_at": "2026-08-24T12:00:00.000Z",
  "aggregate_type": "gift_order",
  "aggregate_id": "GO...",
  "partition_key": "12345",
  "traceparent": "00-...",
  "data": {}
}
```

规则：

- 事件一经发布不可破坏性修改；新增字段保持向后兼容，破坏性修改发布新版本事件。
- 所有消费者以 `event_id` 幂等，不依赖 Kafka 的恰好一次语义。
- Topic 与分区键按需要保持的顺序选择：弹幕、在线和房间统计使用 `room_id`；余额扣款使用 `user_id`；订单状态使用 `order_no`。一个事件不能同时保证多个维度的全局顺序。
- 事件不携带密码、JWT、支付敏感信息；日志与 Trace 遵从同样限制。

建议初始 Topic：

| Topic | 生产者 | 消费者 | 分区键 |
| --- | --- | --- | --- |
| `interaction.danmaku.v1` | 互动接入服务 | 弹幕归档服务 | `room_id` |
| `commerce.gift-order.v1` | 钱包-礼物服务 Outbox | 礼物投递、统计、风控 | `room_id` 或按订单主题另设 `order_no` |
| `room.lifecycle.v1` | 账户-房间服务 | 互动、统计、通知 | `room_id` |
| `identity.user.v1` | 账户-房间服务 | 需要用户读模型的服务 | `user_id` |

若礼物事件既需“按订单顺序”又需“按房间展示顺序”，应发布两个明确语义的事件流或让下游构建读模型；不要混用一个 Topic 的分区键。

## 5. 分阶段实施

### 阶段 0：建立迁移护栏

**目标：** 不改变外部 API 的前提下，为拆分准备度量与契约。

- 将现有 API 定义、错误码、JWT Claim 和 Centrifugo 消息 envelope 固化为版本化契约测试。
- 建立事件 schema 目录、兼容性检查和 DLQ / 重放操作手册。
- 为 MySQL 连接池、Kafka lag、Outbox backlog、Centrifugo 连接数与消息延迟补齐仪表盘和告警。
- 将数据库访问按未来所有者收口，禁止新代码跨模块写表。

**完成门槛：** 契约测试、幂等测试、故障注入与现有 `make test`、M7/M8 冒烟均通过。

### 阶段 1：先拆 Worker Deployment

**目标：** 利用现有 `WORKER_ROLES`，不改变业务代码地获得独立扩缩容。

将 `live-worker` 拆成以下独立 Deployment：

- `outbox-publisher`；
- `gift-delivery-worker`；
- `danmaku-archive-worker`；
- `stats-aggregator-worker`；
- `like-snapshot-worker`。

每个 Deployment 使用最低权限数据库账号、独立资源请求和限额、独立 readiness 指标。Kafka 消费 Worker 根据 lag、处理时延和分区数伸缩；统计 Worker 保持单活或使用明确租约，避免重复广播。

**回滚：** 将所有 role 合并回原 `live-worker` Deployment；数据库、Topic 与 API 均不改变。

### 阶段 2：拆钱包-礼物服务

**目标：** 首先拆出强一致、边界稳定且已有 Outbox 的领域。

- 新建 `live-commerce`（钱包-礼物）进程和内部 Service；Gateway 保持原有 `/api/v1/wallet`、`/api/v1/rooms/{room_id}/gifts` 契约。
- 首先在同一 MySQL 实例中以独立 schema 或独立账号声明表所有权，再评估物理独库。
- 送礼始终在本服务内提交本地事务；礼物实时展示只消费 `gift.order.completed.v1`，不参与交易提交。
- 灰度期间以路由切换而非双写迁移；严禁两个服务同时写钱包或订单表。

**完成门槛：** 余额不为负、重复扣款为零、成功订单必有流水与 Outbox、Outbox 重试及消费者重放正确；性能不低于当前已验证的低延迟工作点。

### 阶段 3：拆互动接入与弹幕归档

**目标：** 将高频、可降级的流量从事务 API 中隔离。

- 新建 `live-interaction` 承担弹幕、点赞、观众心跳、限流和热点保护；它只访问互动 Redis namespace 与必要的房间/治理读模型。
- 新建或独立扩容 `danmaku-archive-worker`；历史查询从归档读模型提供。
- 对房间状态、禁言和封禁采用事件投影/短 TTL 缓存，失效时以明确错误或降级策略处理。
- 保持热点房间采样和保护阈值，不能因服务拆分取消已有降级策略。

**完成门槛：** Kafka 不可用、归档积压、实时平台局部故障三种场景下的用户可见行为已定义且经过故障演练。

**已启动（2026-08-24）：** 已建立 `live-interaction` 进程、Service 和可配置的
strangler 路由。`live-api` 在 `INTERACTION_BASE_URL` 非空时，将 `join`、`leave`、
`danmaku`、`like`、`heartbeat` 五个高频写接口转发至该服务；清空该变量即可原路径
回滚，且不存在双写。互动状态继续唯一写入 Redis，弹幕仍为“先实时发布、Kafka 归档
尽力而为”。当前房间、封禁、禁言和昵称校验仍是**只读过渡依赖** MySQL；阶段 4 前
必须以房间/治理、身份投影或版本化查询 API 替换，并为服务配置只读数据库账号，不能
将此过渡依赖固化为跨服务数据库访问。

### 阶段 4：拆账户-房间与引入 Gateway

**目标：** 完成控制面拆分，同时保持客户端单一入口。

- 新建 `live-identity-room`，拥有认证、用户、房间生命周期与治理规则。
- Gateway 仅执行鉴权、路由、边缘限流、请求 ID/Trace 传播与少量 BFF 聚合；不得承载业务表访问或转变为新的单体。
- 互动服务通过房间/治理读模型工作，钱包服务以可信 `user_id` 和 `room_id` 执行授权校验。

**完成门槛：** 一次请求的 Trace 可跨 Gateway、至少一个业务服务、Kafka 消费者和实时投递串联；服务故障隔离演练通过。

**已启动（2026-08-24）：** `live-identity-room` 已接管认证、用户、房间生命周期、禁言和封禁的外部 v1 路由；`live-api` 以 `IDENTITY_ROOM_BASE_URL` 作为可回滚的网关路由开关。该服务是 `users`、`live_rooms`、`room_mutes`、`room_bans` 的唯一写入者。互动服务仍需在下一步以身份/房间治理投影或版本化 API 消除其临时只读 MySQL 依赖；在该项完成前，阶段四不得视为完成。

### 阶段 5：基础设施高可用与弹性伸缩

**目标：** 服务拆分后再获得真实高可用，而非仅增加 Pod 名称。

- Centrifugo 使用多副本、负载均衡以及 Redis 高可用；连接数与广播延迟达到资源阈值时扩容。
- Kafka 采用生产级多 Broker、复制、`min.insync.replicas`、ACL、TLS/SASL 与跨可用区部署；Topic 分区数根据消费者并行度规划。
- MySQL 采用托管高可用或主从/集群方案，定义备份、PITR、演练和连接总预算。
- 配置 PDB、topology spread、NetworkPolicy、Secret 管理、限额和 HPA/KEDA。HPA 支持资源与自定义指标，但自动伸缩不能替代容量测试；参考 [Kubernetes HPA](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)。

**完成门槛：** 多可用区故障、单节点下线、Kafka Broker 故障、Redis failover、数据库主切换均完成演练并满足约定 RTO/RPO。

## 6. 技术取舍

| 方案 | 复杂度 | 独立扩缩容 | 数据一致性 | 当前建议 |
| --- | --- | --- | --- | --- |
| 保持当前模块化单体 + Worker role 拆分 | 低 | Worker 高、API 中等 | 最简单可靠 | 立即实施 |
| 渐进式 3--5 个业务服务 | 中 | 高 | 本地事务 + 事件最终一致 | 推荐目标 |
| 目录级十余服务 + 独库 | 很高 | 表面很高 | 跨服务一致性复杂 | 不推荐 |
| 同步 RPC 编排所有业务 | 中高 | 一般 | 级联故障风险高 | 仅用于必要的强同步查询 |

事件驱动并不意味着所有请求异步化：登录、余额查询、送礼受理、房间权限等仍必须同步返回明确结果；异步化的是归档、投递、统计、通知和读模型更新。

## 7. 运行与治理要求

- 每个服务必须具备 `/health`、`/ready`、结构化日志、Prometheus 指标和 OpenTelemetry Trace。
- 每个 Kafka consumer group 都必须监控 lag、重试、DLQ、处理延迟、去重次数和重放结果。
- 每次扩容 API Pod 前，先验证总 MySQL 最大连接预算；不能将当前单进程 `MYSQL_MAX_OPEN_CONNS=40` 原样复制到每个 Pod。
- API、实时、Kafka、Redis、MySQL 分别制定 SLO；不得用“服务数量”或单个饱和 TPS 作为成功指标。
- 数据迁移采用 expand/contract：先增加兼容字段/读路径，完成回填与校验后切流，最后删除旧路径。任何删除均需要备份与回滚窗口。

## 8. 非目标

- 本计划不包含视频推流、转码、录制和 CDN。媒体平面应独立接入 SRS、LiveKit 或云直播能力，不能与互动事务和实时消息服务耦合。
- 本计划不引入分布式事务、服务网格、CQRS/ES 全量改造或 Redis Cluster，除非对应的容量或组织边界已有可测量需求。
- 本计划不承诺未经多节点压测验证的连接数、TPS、RTO 或 RPO。

## 9. 成功判定

微服务化完成不以“拆了多少服务”衡量，而以以下结果衡量：

1. 热点房间、异步归档、礼物交易可独立扩缩容且不互相抢占资源；
2. 钱包、订单、流水与 Outbox 不变量在故障和重试下保持正确；
3. 任一服务无法通过跨库写入破坏其他服务的数据所有权；
4. 单个消费者、Centrifugo 节点或应用 Pod 故障不会造成不可恢复的数据不一致；
5. 多节点压测和故障演练得到可复现的容量与恢复结论。
