# 直播互动系统压测与容量规划方案

**文档版本：V1.0**  
**测试对象：Go + Centrifugo + Redis + Kafka + MySQL 直播互动系统**

---

# 1. 测试目标

压测不以证明某个框架“能支撑百万并发”为目标，而是建立当前硬件和配置条件下的真实容量模型。

最终需要回答：

```text
单台 Centrifugo 可以维持多少连接？

单台 Centrifugo 可以支撑多少消息吞吐？

单热门直播间最多允许多少在线人数？

Redis 在什么吞吐下出现瓶颈？

点赞聚合能降低多少广播流量？

Kafka 最大可接受 Lag 是多少？

礼物 TPS 能达到多少？

系统应该在什么指标下开始扩容？
```

---

# 2. 压测原则

采用：

```text
组件压测
   ↓
单链路压测
   ↓
系统联合压测
   ↓
峰值压测
   ↓
故障压测
```

不得直接从：

```text
0
```

跳到：

```text
100 万连接
```

否则无法准确定位瓶颈。

记录：

```text

CPU
Memory
GC
File Descriptor
Network Connection

Disconnect Rate

```

计算：

```text
Memory Per Connection
=
Memory Increase / Connection Count
```

例如测试得出：

```text

Memory Before = 300MB
Memory After  = 1.8GB
```

则：

```text
约 15KB / Connection
```

这里只允许记录实际压测数据，禁止提前假定。

# 9. 空连接验收

需要满足：

```text
连接成功率 ≥ 99.9%
无持续内存增长
CPU 保持安全余量
无异常大量断开
```

容量不能定义在 CPU 100%。

建议规划最大利用率：

```text
CPU ≤ 60~70%
Memory ≤ 70%
```

剩余容量应对突发流量和重连。

# 13. 广播放大模型

定义：

```text
N = 在线用户
M = 每秒广播消息
S = 单消息平均大小
```

理论应用层下行数据：

```text
Bandwidth ≈ N × M × S
```

例如仅用于容量推导：

```text
N = 100,000

M = 100 msg/s

S = 300 Bytes
```

则：

```text
100,000 × 100 × 300
=
3,000,000,000 Bytes/s
```

约：

```text
3 GB/s
```

且这还没有包含：

```text
WebSocket Frame
TCP
TLS
协议字段
系统开销
```

因此热门直播间真正的瓶颈往往首先变成：

```text
Network Egress
```

而不是 CPU。

所有容量设计都必须首先计算消息放大。

# 37. 容量模型

建立三个基本容量参数：

```text
C_conn
=
单台 Centrifugo 最大安全连接数

C_msg
=
单台 Centrifugo 最大安全消息吞吐

C_bw
=
单台服务器最大安全网络吞吐
```

实际容量：

```text
C_actual
=
min(
 C_conn,
 C_msg,
 C_bw
)
```

不能仅根据 Connection Capacity 扩容。

# 38. Centrifugo 节点计算

假设实际压测得到：

```text
单节点安全连接容量 = X
```

平台峰值连接：

```text
PeakConnections = P
```

冗余系数：

```text
R = 1.5
```

则：

```text
NodeCount
=
ceil(P / X × R)
```

例如仅作公式演示：

```text
P = 1,000,000

X = 100,000

R = 1.5
```

则：

```text
15 Nodes
```

实际 X 必须来自压测。

---

# 39. N+1 容灾要求

不能按照：

```text
所有节点 100% 满负载
```

规划。

应该满足：

```text
任意 1 个节点故障
```

剩余节点仍可承载连接。

因此：

```text
Normal CPU < 70%
```

是更合理的目标。

---

# 40. 带宽规划

定义：

```text
U = 房间用户数
R = 广播消息/s
S = 平均消息大小 Bytes
```

应用层理论带宽：

```text
B = U × R × S
```

再乘安全系数：

```text
1.2 ~ 1.5
```

用于协议和突发开销。

热门直播间的容量评估首先应计算：

```text
B
```

如果理论带宽已经超过网卡极限，再增加 CPU 没有意义。

---

# 41. Kafka 容量

定义：

```text
Q = 每秒事件数
S = 平均事件大小
Replication = R
```

粗略写入量：

```text
WriteBandwidth
≈
Q × S × R
```

同时考虑：

```text
Retention
```

计算磁盘。

例如：

```text
Daily Storage
≈
Q × S × 86400 × Replication
```

真实系统还需要预留索引、日志段和峰值空间。

---

# 42. MySQL 容量

分开计算：

```text
礼物 TPS
```

和：

```text
弹幕日志写入 TPS
```

资金库不建议因为弹幕日志而受到影响。

如果未来弹幕量巨大，可以将：

```text
业务数据库
```

与：

```text
互动日志存储
```

拆开。

---

# 43. 自动扩容指标

Centrifugo 不建议只依据 CPU 扩容。

可以综合：

```text
Connections Per Node
CPU
Network Throughput
Publish Latency
```

例如：

```text
connections > 70% safe capacity

OR

CPU > 65% 持续 5min

OR

network > 65%

OR

P99 latency > threshold
```

触发扩容。

---

# 44. Go API 扩容

主要指标：

```text
CPU
QPS
P99
Goroutine
DB Pool Wait
```

如果：

```text
CPU 很低
但 DB Pool Wait 很高
```

继续增加 Go 实例反而可能加重 MySQL 压力。

扩容必须判断真实瓶颈。

---

# 45. Kafka Consumer 扩容

观察：

```text
Consumer Lag
```

如果 Lag 持续上涨：

```text
ProduceRate > ConsumeRate
```

需要：

```text
增加 Consumer
```

但最大并发能力受：

```text
Partition Count
```

限制。

因此 Topic Partition 数量应预留水平扩展空间。

